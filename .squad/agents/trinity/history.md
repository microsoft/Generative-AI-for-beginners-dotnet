- AI logic must stay behind service classes — never call models directly from UI or game logic.
- The "Core Samples" CI check (`build-validation.yml`) fails on `ubuntu-latest` with NETSDK1100 because 5 `CoreGenerativeAITechniques.sln` projects target `net8.0-windows10.0.18362`/`win-x64` (Foundry Local WinML/NAudio/Whisper samples: `06-foundrylocal-native-auto-chat`, `05-foundrylocal-audio-transcription`, `10-live-speech-to-text`, `11-foundrylocal-live-transcription`, `04-foundrylocal-native-chat-completions`). The fix is `-p:EnableWindowsTargeting=true` on both the shared `dotnet restore` and `dotnet build` steps in the matrix (not a per-project `.csproj` change) — proven green on PR #526 commit `4e045bb`, and reproduced clean locally via `dotnet build samples/CoreSamples/CoreGenerativeAITechniques.sln --no-restore --configuration Release -p:EnableWindowsTargeting=true` (0 errors, all 5 Windows-targeted DLLs produced).
- 2026-08-22: Extracted that fix as a standalone branch `fix/enable-windows-targeting-ci` (commit `5a6d941`, from clean `main` @ `bd4e082`) to unblock #527/#528's inherited-red Core Samples check per Morpheus's reviewer-gate decision and Mouse's validation notes. `git push -u origin fix/enable-windows-targeting-ci` failed with a 403 + "organization has enabled or enforced SAML SSO... re-authorize the OAuth Application 'GitHub CLI'" — same SAML wall `gh pr view 526`/`gh pr diff 526` hit earlier in the session. `git ls-remote`/`git fetch` on public refs (e.g. `refs/pull/526/head`) work fine over this token even when GraphQL/push are SAML-blocked, which is useful for read-only diff inspection when `gh pr diff` is unavailable.
- 2026-08-22 (later same day): That CI-unblocker branch merged as PR #529 (commit `d3d0bff`) — the earlier SAML push block was transient/session-specific, not permanent; a later push in this same environment (updating PR #527's `dependabot/github_actions/...` branch) succeeded without any re-auth step. Don't assume one blocked `gh`/git-push call means auth is broken for the rest of the session — retry the actual operation later rather than treating the earlier failure as a standing fact.
- Pattern: for follow-up work on someone else's open PR branch (e.g. a dependabot branch) while the main checkout has unrelated dirty/uncommitted files from other agents, use `git fetch origin <branch>` + `git worktree add ../<repo>-prNNN -B <branch> FETCH_HEAD` to get an isolated worktree instead of switching the shared main checkout. Clean up after with `git worktree remove` + `git branch -D <local-branch>` (this only removes the local worktree branch ref, not the remote branch — safe to do even though the branch is still open on origin).
- Gotcha verifying GitHub Action SHA pins against tags: `git ls-remote --tags <repo>` lists **annotated** tags as two lines — the tag object SHA on `refs/tags/vX.Y.Z` and the actual commit it points to on `refs/tags/vX.Y.Z^{}`. Pinned `uses: owner/action@<sha>` values reference the **commit**, so always compare against the `^{}` dereferenced line, not the bare tag line, or you'll get false mismatches (e.g. `actions/github-script@v9.0.0`'s tag object is `d746ffe3...` but the pinned/correct commit is `3a2844b7...`).
- 2026-08-22: Remediated PR #526 (`bruno-addAzFncSample`, `AzFunction-BasicChat-01` sample) in an isolated worktree while #528 awaited CLA. Merging current `origin/main` (which already carried #527 + #529) into the stale PR branch was a **clean, zero-conflict** merge via git's `ort` strategy — worth noting since the PR branch's own `.sln` edits happened to also fix an unrelated pre-existing bug on `main` (`CoreGenerativeAITechniques.sln` missing an `EndProject` line after `DataIngestion-01-Simple`, present since merge-base `dbda04d`); don't "fix" that kind of thing separately on `main` if a pending PR already carries the fix as an incidental side effect.
- Repo convention confirmed via repo-wide grep: nearly all sample `.csproj` files share one `UserSecretsId` value, `genai-beginners-dotnet`, rather than a per-project random GUID (a few legacy exceptions: McpSample.*, SpaceAINet.*, HFMCP.GenImage.AppHost). Flag a fresh random GUID in new sample PRs as a fixable nit.
- Repo-root `.vscode/settings.json` should stay untouched by individual sample PRs — the established, portable pattern for VS Code extension settings that only apply to one sample (e.g. `azureFunctions.projectSubpath`) is a **sample-local** `.vscode/settings.json` inside that sample's own folder (precedent: `samples/CoreSamples/AgentLabs-03-PythonParksInformationServer/.vscode/settings.json`), using a relative value like `"."` so it's portable across OSes and doesn't assume the whole repo is the open workspace.
- When wiring a new xUnit test project into `build-validation.yml`'s Core Samples matrix leg, add a narrowly-scoped `dotnet test <path-to-test-csproj> --no-build` step gated with `if: matrix.solution.name == 'Core Samples'`, rather than `dotnet test <sln>` — keeps CI fast and avoids solution-wide test discovery overhead when there's only one test project.
- For a new sample's Bicep storage account, `allowSharedKeyAccess: false` is safe to add once you've verified the identity-based `AzureWebJobsStorage__accountName/__clientId/__credential=managedidentity` app settings *and* the matching `Storage Blob Data Owner`/`Storage Queue Data Contributor`/`Storage Table Data Contributor` role assignments are all already wired — confirm both pieces exist before flipping this, and validate non-destructively via `az deployment sub what-if` (no resources created) before considering it proven.
- Full local Functions smoke-testing pattern that worked well: run Azurite (`azurite --silent --location .`) from a data directory **inside the worktree** (e.g. `<worktree>/_azurite-data`) so cleanup is just `git worktree remove`; copy `local.settings.json.example` → `local.settings.json` (already gitignored) with a real Foundry endpoint/deployment pointed at an existing personal Foundry resource; run `func start`; hit negative cases (malformed JSON, missing/over-length fields → expect 400s) and one real positive request via `Invoke-RestMethod`/`curl.exe`; then check the func host log output to confirm no request/response content or secrets were logged (only execution IDs/timing should appear) before deleting the Azurite data dir and the local secrets file.
- When committing several independent reviewer fixes as separate commits, remember `git reset --soft` only moves `HEAD` — it does **not** unstage prior `git add`s, so a stray earlier `git add` (e.g. from an unrelated file restore) will bleed into the next `git commit -m ...` you make. Use `git reset` (mixed, no `--soft`) between commits when you need genuinely clean, non-overlapping staged diffs per commit.
