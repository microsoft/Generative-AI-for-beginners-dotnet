# Project Context

- **Owner:** Copilot
- **Project:** Generative AI for Beginners .NET — a hands-on course teaching .NET developers to build Generative AI applications with runnable samples.
- **Stack:** .NET 10+, Microsoft.Extensions.AI (MEAI), Microsoft Agent Framework (MAF), Azure OpenAI, Ollama, Aspire, Blazor
- **Created:** 2026-07-15

## Learnings

<!-- Append new learnings below. Each entry is something lasting about the project. -->
- Lessons live in numbered folders `01-`–`05-`; all code samples live under `samples/` (CoreSamples, MAF, AppsWithGenAI, PracticalSamples).
- CI-validated solutions: CoreSamples, Aspire.MCP.Sample, HFMCP.GenImage, SpaceAINet, MAF-Demos.
- Never hardcode API keys — use `dotnet user-secrets` or environment variables. AI providers abstracted behind service classes.
- `CoreGenerativeAITechniques.sln` contains 5 projects targeting `net8.0-windows10.0.18362` (Foundry Local native/audio samples + LiveSpeechToText). They cannot restore on `ubuntu-latest` without `-p:EnableWindowsTargeting=true`, so Core Samples CI is red on `main` for every PR that triggers it.
- .NET 10 file-based apps (`dotnet run app.cs`) default `JsonSerializer.IsReflectionEnabledByDefault` to **false**. Any file-based sample whose SDK serializes with reflection (e.g. OllamaSharp) fails at the first model call unless it declares `#:property JsonSerializerIsReflectionEnabledByDefault=true`. Project-based samples are unaffected and do not set the property.
- `build-validation.yml` only triggers on `pull_request` with a `samples/**` path filter. There is no `push`/`main` trigger, so `main` is never build-validated after a merge — post-merge green is not observable from CI.
- `main` has **no branch protection and no rulesets**. Required checks and required reviews are not enforced by the platform; the reviewer gate is entirely human. A red required-looking check will not block a merge.
- Only `welcome-pr.yml` uses `pull_request_target`, and it has no `actions/checkout` step, so untrusted fork code is never executed. Its inline scripts read `context.payload.sender.login` as a JS value, not via `${{ }}` interpolation, so there is no expression-injection sink.
- Workflow inline scripts only use `require('fs')` (a Node builtin) and never `require('@actions/github')` or a `getOctokit` redeclaration, so `actions/github-script` v9's ESM breaking changes do not affect this repo.
- `CONTRIBUTING.MD` mandates the shared `UserSecretsId` `genai-beginners-dotnet` for every sample. New sample projects that scaffold a random GUID violate this.
- Lesson READMEs (e.g. `03-AIPatternsAndApplications/readme.md`) are the sample index — there is no `samples/CoreSamples/README.md`. A new sample is undiscoverable until it is added to a lesson README table.
- Dependabot's `# vN` trailing comments are not trustworthy: in PR #527 it moved `pozil/auto-assign-issue` to the v4.0.1 commit while leaving the comment `# v1`. Always resolve the pinned SHA against the upstream tag before approving.
- The local `gh` token authenticates as `elbruno`, who authors most maintainer PRs. GitHub rejects `gh pr review --approve` on your own PR (`Can not approve your own pull request`). Post the gate evidence with `gh pr review --comment` and require a second maintainer account for the formal approval.
- Microsoft SAML authorization for `gh` is now granted: `gh api` and `gh run view --job <id> --log` work against this repo, so Actions job logs are directly readable instead of having to infer failures from check-run annotations.
- Adding `-p:EnableWindowsTargeting=true` to the shared matrix steps in `build-validation.yml` is a no-op for the four solutions without Windows-targeting projects. With it, the Linux Core Samples build reports `29 Warning(s) / 0 Error(s)` — identical to a local Windows Release build, so Linux CI has real parity rather than a partially-skipped build. The flag only permits restoring Windows targeting packs; it does not suppress compiler errors, so it cannot mask a regression.
- GitHub's self-approval block keys on the PR **author**, not on who pushed commits. `elbruno` could not approve his own PR #529, but could approve #527 (author `dependabot[bot]`) even after pushing two commits to that branch. So a maintainer can always formally approve a bot-authored PR they have amended.
- When a PR branch is synced with `main` so its merge base equals current `origin/main`, `git diff origin/main...head` and `git diff origin/main head` return identical output. That equality is the cheapest proof that CI ran on exactly what will land — check it before trusting a green run on a long-lived branch.
- `gh api <commit>/status` returns `state: pending` with an empty `statuses` array when a repo publishes only **check runs** and no legacy commit statuses. Do not read that as a failing gate; use `<commit>/check-runs` instead. Here `license/cla` is a check run reporting "All CLA requirements met".
- Resolving a pinned action SHA to its tag needs annotated-tag dereferencing: `git/matching-refs/tags` returns `object.type: "tag"` for annotated tags, whose `object.sha` is the tag object, not the commit. Follow up with `git/tags/<sha>` or the mapping silently misses.
- Pushing human commits to a Dependabot branch stops Dependabot from rebasing or recreating it. Once a maintainer amends a dependency PR (as on #527), it will drift silently against `main` — merge it promptly rather than letting it sit.
- `.github/workflows` still contains one unpinned mutable ref, `IEvangelist/profanity-filter@main`. Dependabot cannot manage branch refs, so it will never appear in a bump PR and needs a manual SHA pin.
- Setting `allowSharedKeyAccess: false` on a Functions storage account is only safe when the host connection is switched to identity-based in the same change: `AzureWebJobsStorage__accountName` + `__clientId` + `__credential: managedidentity`, plus Blob Data Owner / Queue Data Contributor / Table Data Contributor on the account. Half of that pairing bricks the Function at runtime, and Bicep still compiles — review both halves together.
- `build-validation.yml` now runs `dotnet test` for the `Core Samples` leg only, keyed on `matrix.solution.name == 'Core Samples'` with one hardcoded project path. `AzFunction-BasicChat-01.Tests` is the only test project under `samples/`, so coverage is complete today, but a second test project or a matrix rename would go unrun silently.
- Sample-local `.vscode/settings.json` with `"azureFunctions.projectSubpath": "."` is the portable pattern for this repo. Never put per-sample tooling paths in the root `.vscode/settings.json`, and never use backslashes — Linux Codespaces is a first-class target.
- A green check is not proof a test step executed. The `if:` guard can skip it and the job still reports success. Pull the job log and look for the actual `Passed! - Failed: 0, Passed: N` line before crediting a "CI runs the tests" remediation.
- `.gitattributes` now carries `*.sh text eol=lf`. Any sample shipping shell scripts needs this, otherwise a Windows checkout writes CRLF and bash fails with a confusing `\r` error on the shebang line.
- The `02 Functions` solution folder in `CoreGenerativeAITechniques.sln` is `{F5798C6F-98D6-4411-A5F0-F928CBA64095}`. New Functions samples nest there via `GlobalSection(NestedProjects)`.
- Proportionality rule for the gate: block on security, correctness, CLA, or convention violations that ship to learners; record unrelated one-line scope creep as a required follow-up instead. Blocking a fully-remediated, fully-green sample over a courtesy-bot trigger tweak costs more than it protects.
- `welcome-pr.yml` attributes its thanks comment to `context.payload.sender.login`. That equals the PR author only on `opened`. If the trigger ever gains `reopened`, switch to `context.payload.pull_request.user.login` or the bot will @-mention whoever reopened the PR.
- File-based samples (`app.cs` with `#:package`, no `.csproj`) are **not** in any solution, so `dotnet build <sln>` never compiles them and CI cannot catch regressions in them. A green Core Samples check says nothing about these 13 files — they must be validated by actually running them. This is why the OllamaSharp reflection bug reached `main`.
- Best proof that `JsonSerializerIsReflectionEnabledByDefault=true` works when the model isn't pulled: without it the app throws `InvalidOperationException` inside `JsonSerializer.Serialize`; with it the same app reaches `SendToOllamaAsync` and fails with `404`. The failure moving from serialization to transport is stronger evidence than substituting a different model.
- OllamaSharp's streaming path (`GetStreamingResponseAsync`) hits the same reflection barrier as `GetResponseAsync` — verified with paired probe apps. Don't assume streaming differs when auditing which samples need the property.
- Only 3 of the 13 file-based samples under `samples/` use OllamaSharp and need the reflection property. The rest use `Azure.AI.OpenAI`/`OpenAI` (System.ClientModel, no reflection-based STJ) or `LlmTornado`, and are unaffected.
- `BasicChat-10ConversationHistory` silently picks Foundry over Ollama whenever `AzureOpenAI:Endpoint` exists in the shared `genai-beginners-dotnet` secrets store. On a maintainer machine the Ollama fallback never runs, so reproduce that branch with a standalone probe rather than concluding the path is fine.
- A CLA check reporting `queued` with title "Contributor License Agreement is not agreed yet" is a hard merge gate, not a pending build. Approve on technical merit if warranted, but state explicitly that approval is not merge authorization — `main` has no branch protection, so nothing platform-side prevents a premature merge.
