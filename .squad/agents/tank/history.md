### 2026-08-22 — PR #528 and #526 AI/provider validation
- Every project-based `.csproj` sample in `samples/CoreSamples` and `samples/MAF` (~47 files) uses the literal shared `<UserSecretsId>genai-beginners-dotnet</UserSecretsId>` — never a generated GUID. Verified by grep across both trees. Enforce this on any new project-based sample.
- `dotnet run app.cs` file-based apps default `JsonSerializerIsReflectionEnabledByDefault=false`, which breaks any package (e.g. `OllamaSharp`) that reflection-serializes its request payload. Fix is `#:property JsonSerializerIsReflectionEnabledByDefault=true` in the file's `#:` header — confirmed by reproducing `System.InvalidOperationException: Reflection-based serialization has been disabled...` on unfixed copies of `BasicChat-03Ollama/app.cs`, `BasicChat-10ConversationHistory/app.cs`, and the untouched `BasicChat-07Ollama-gpt-oss/app.cs`, then confirming real Ollama (`phi4-mini`) responses after adding the property. Project-based samples (`.csproj`) are unaffected because MSBuild-based apps default that property to `true`.
- Repo-wide `.github/workflows/build-validation.yml` builds on `ubuntu-latest` without `-p:EnableWindowsTargeting=true`; any solution containing a Windows-TFM project (e.g. `net8.0-windows10.0.18362` FoundryLocal samples) fails CI with "set the EnableWindowsTargeting property to true" even though it builds fine locally on Windows. This is a main-inherited defect, not something introduced by unrelated PRs — always check check-run annotations before blaming a PR's diff for a red "Core Samples" build.
- `build-validation.yml` only runs `dotnet restore`/`dotnet build`, never `dotnet test` — new xUnit test projects added to `CoreGenerativeAITechniques.sln` build in CI but their tests are not automatically executed there.
- To inspect a PR's real file tree without touching the working repo: `git fetch origin pull/<N>/head:pr-<N>-review` then `git worktree add <path-outside-repo> pr-<N>-review`; remove after with `git worktree remove --force` (fall back to `cmd /c rmdir /s /q` for long Azure Functions build-output paths that exceed `MAX_PATH`) and `git branch -D`.

### 2026-08-22 — PR #528 follow-up: closed the scope gap and pushed to a fork PR
- `gh` CLI splits cleanly by transport: GraphQL-based porcelain (`gh pr view`, `gh pr checks`, etc.) is blocked by Microsoft org SAML enforcement, but `gh api` (REST) works fully authenticated, including writes (`gh api -X PATCH repos/<owner>/<repo>/pulls/<n> -F body=@file.md` succeeded to edit a PR body). Anonymous `curl.exe` to `api.github.com` REST endpoints also works for public repos. Prefer `gh api`/REST over `gh pr`/`gh issue` porcelain in this environment.
- Pushing to a contributor's fork branch (`git push <fork-remote> <local-branch>:<their-branch>`) succeeds over HTTPS using `gh`'s installed git credential helper (`gh auth setup-git`), provided the PR has `maintainer_can_modify: true` and the authenticated user has write/admin access to the upstream repo. This is a distinct code path from `gh pr` GraphQL calls and is **not** blocked by the SAML restriction that blocks GraphQL — confirmed by successfully pushing a commit to `matheuscardosolazzarini/Generative-AI-for-beginners-dotnet:main` (PR #528's head) and seeing the PR's `head.sha` update immediately via the REST API.
- After a maintainer-initiated push to a fork PR branch, GitHub re-triggers `pull_request` workflows but sets them to `action_required` (not queued to run) — this is the standard "approve workflow runs for a fork PR" security gate, separate from PR review approval. It requires an explicit maintainer click ("Approve and run workflows") in the Actions UI or the `POST /actions/runs/{id}/approve` REST endpoint; treat this the same as "approve" and leave it to a human unless explicitly asked to unblock CI.
- Repo-wide, exactly three file-based (`dotnet run app.cs`, `#:package`-style) samples use `OllamaSharp`: `BasicChat-03Ollama`, `BasicChat-10ConversationHistory`, `BasicChat-07Ollama-gpt-oss`. Any future fix to the file-based reflection-serialization default should touch all three — grep `#:package OllamaSharp` across `samples/` to confirm the full set before considering such a fix complete.
- PR #529 (merged separately, independently of #528) already fixed the `EnableWindowsTargeting` CI gap flagged in the earlier validation pass — `build-validation.yml` on `main` now sets `-p:EnableWindowsTargeting=true` on both restore and build steps. Merging/rebasing an older PR onto current `main` can silently resolve previously-flagged CI defects; always re-check `main` before re-flagging a stale CI issue.
